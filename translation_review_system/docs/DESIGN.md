# DESIGN：架构设计与模块说明

## 1. 总体架构

架构图文件：`docs/architecture-overview.mmd`。

核心链路：

```text
用户输入 → 复杂度评估 → 路由决策 → 模型A/模型B翻译 → 规则评分 → 审校子Agent → 推荐译文
```

## 2. 模块职责

| 文件 | 职责 |
|---|---|
| `src/app.py` | Streamlit 前端界面，负责输入、展示结果、下载评测数据 |
| `src/pipeline.py` | 串联完整业务流程，是系统主编排器 |
| `src/complexity.py` | 自主实现文本复杂度评估和术语表加载 |
| `src/router.py` | 根据复杂度结果做路由决策 |
| `src/translator.py` | 构造翻译提示词，调用两个模型 |
| `src/llm_client.py` | OpenAI 兼容调用客户端与离线模拟客户端 |
| `src/scoring.py` | 可复现的规则评分模型 |
| `src/reviewer_agent.py` | 审校子 Agent，输出信达雅评分与建议 |
| `src/metrics.py` | 中间件：统计模型调用耗时、token 和成本 |
| `src/batch_doc.py` | Markdown 文档批量翻译并保持目录结构 |
| `src/ocr.py` | 图片文字 OCR 提取 |
| `src/tools.py` | LangChain `@tool` 示例，满足工具化要求 |

## 3. 数据流

1. 用户在界面输入文本。
2. `TranslationPipeline.run()` 接收文本。
3. `ComplexityEvaluator.evaluate()` 计算复杂度。
4. `decide_route()` 根据复杂度选择策略。
5. `TextTranslator.translate_many()` 调用模型 A 和模型 B。
6. `CallStatsMiddleware.invoke()` 包裹每次模型调用，记录耗时和成本。
7. `TranslationScorer.score()` 对每个译文进行规则扣分。
8. `ReviewAgent.review()` 生成信达雅评分和建议。
9. 系统按分数选出推荐译文并返回结构化结果。
10. `app.py` 将结果渲染为对比表、评分表、建议和统计信息。

## 4. 复杂度评分公式

总分 100，实际由三部分相加后截断到 100：

```text
复杂度总分 = 句长分 + 从句分 + 术语密度分
```

### 4.1 句长分

| 平均句长 | 分数 |
|---|---:|
| ≤ 12 | 5 |
| 13-20 | 15 |
| 21-30 | 25 |
| 31-45 | 34 |
| > 45 | 40 |

### 4.2 嵌套从句分

通过以下规则估算：

- 英文关系词/从属连词：which、that、although、because 等。
- 中文关联词：因为、虽然、如果、导致、同时、其中等。
- 分号、冒号、括号。
- 一个句子中逗号超过 3 个，视为长链结构。

```text
从句分 = min(30, 嵌套从句数 × 5)
```

### 4.3 术语密度分

```text
术语密度 = 命中术语数 / token数量 × 100
```

| 术语密度 | 分数 |
|---|---:|
| ≤ 1 | 3 |
| 1-3 | 10 |
| 3-6 | 20 |
| > 6 | 30 |

## 5. 路由策略

| 复杂度 | 策略 |
|---|---|
| < 35 | 两个模型都译，模型 A 作为快速译文，模型 B 作为对照 |
| 35-69 | 两个模型都使用术语提示，启用审校 Agent |
| ≥ 70 | 强制术语表，启用严格审校，优先选择术语一致性高的译文 |

说明：为满足课程要求“两个模型翻译同一文本并对比”，演示和评测时始终调用两个模型；路由主要控制提示词强度和审校策略。

## 6. 评分模型设计

所有扣分由 `src/scoring.py` 自主实现，不由 LLM 决定。这样答辩时能解释清楚“为什么扣分”。

| 规则 | 扣分方式 | 目的 |
|---|---:|---|
| 数字/单位遗漏 | 每处 -8，最多 -24 | 防止金额、比例、年份丢失 |
| 专业术语不一致 | 每处 -6，最多 -30 | 保证术语表一致 |
| 源语残留偏多 | -10 或 -20 | 防止大段英文没翻 |
| 译文长度异常 | 过短 -15，过长 -8 | 检测漏译或过度扩写 |
| 标点/括号结构错误 | 每类 -5，最多 -15 | 保证格式结构可读 |
| 专名/缩写遗漏 | 每处 -4，最多 -12 | 保护 API、GDP 等关键名词 |
| 重复/语病 | 每处 -5，最多 -15 | 提升表达质量 |
| Markdown 结构丢失 | 每处 -8，最多 -24 | 批量文档翻译保持目录结构 |

## 7. 技术选型

| 技术 | 原因 |
|---|---|
| Python | 适合快速实现规则、调用模型、做数据处理 |
| Streamlit | 前端简单，答辩可以直接跑界面 |
| OpenAI 兼容接口 | 可接入多个模型厂商或本地 LM Studio |
| CSV 术语表 | 易编辑、可复核、适合课程验收 |
| pytesseract | OCR 实现简单，属于可选进阶功能 |
| LangChain `@tool` | 满足工具化要求，也便于后续改成 Agent |

## 8. 边界处理

- 空输入：直接提示“输入文本不能为空”。
- 模型 Key 缺失：使用 MOCK_MODE 离线演示。
- OCR 失败：返回 warning，不阻塞文本翻译主流程。
- Markdown 代码块：不翻译，避免破坏代码。
- 评分不确定：规则只做自动初筛，最终建议人工复核。
