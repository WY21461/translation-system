# ANALYSIS：需求分析、用例与详细实现过程

## 1. 课题要求拆解

原题：序号 21「多模型协作翻译与审校系统」。

基本要求拆成 4 个必须完成的验收点：

1. 文本复杂度评估自主实现：句子长度、嵌套从句数、专业术语密度。
2. 审校评分模型至少 5 条可量化扣分规则。
3. 至少 10 段不同领域文本，对比两个模型评分与耗时。
4. 输出原文、多译文对比、评分表、推荐译文。

进阶要求拆成 4 个可选加分点：

1. 审校子 Agent：信达雅评分与修改建议。
2. OCR：图片文字提取并翻译。
3. 批量文档翻译保持目录结构。
4. 中间件统计模型调用成本与耗时。

## 2. 用户使用场景

### 场景 A：单段文本翻译对比

1. 用户输入英文段落。
2. 系统计算复杂度。
3. 系统调用两个模型生成译文。
4. 系统对两个译文分别扣分。
5. 系统输出推荐译文和审校建议。

### 场景 B：专业文本审校

1. 用户输入医学、法律、科技文本。
2. 系统命中术语表。
3. 路由策略要求强制术语表。
4. 如果译文没有采用标准译法，评分器扣分。
5. 审校 Agent 提示“统一专业术语”。

### 场景 C：Markdown 文档翻译

1. 用户粘贴 Markdown 文档。
2. 系统提取标题作为目录。
3. 系统逐段翻译标题和正文。
4. 代码块不翻译。
5. 输出保持标题层级和列表结构的 Markdown。

### 场景 D：图片文字翻译

1. 用户上传图片。
2. OCR 提取图片文字。
3. OCR 结果进入文本翻译主流程。
4. 如果 OCR 不可用，系统给出可读错误，不崩溃。

## 3. 详细开发过程

### 第 1 步：确定项目结构

先建一个 Python 项目，分成代码、数据、文档三类：

```text
src/    核心代码
data/   术语表和测试文本
docs/   需求、设计、部署、测试文档
```

这样做的好处是答辩时能清楚说明每个文件的职责。

### 第 2 步：准备术语表

创建 `data/term_glossary.csv`，字段为：

```csv
source_term,target_term,domain
artificial intelligence,人工智能,technology
clinical diagnosis,临床诊断,medicine
```

术语表有两个作用：

1. 复杂度评估：命中术语越多，专业术语密度越高。
2. 审校评分：如果原文出现术语但译文没有标准译法，就扣分。

### 第 3 步：实现复杂度评估

对应文件：`src/complexity.py`。

#### 3.1 句子长度

先把文本按句号、问号、感叹号、换行切分句子，再统计 token 数。

```text
平均句长 = token总数 / 句子数
```

然后按区间给分：

- ≤12：5 分
- 13-20：15 分
- 21-30：25 分
- 31-45：34 分
- >45：40 分

#### 3.2 嵌套从句数

不让 LLM 判断，而是用规则估计：

- 英文标记：which、that、because、although、if 等。
- 中文标记：因为、虽然、如果、导致、其中等。
- 分号、冒号、括号。
- 一个句子逗号很多，也认为结构复杂。

```text
从句分 = min(30, 嵌套从句数 × 5)
```

#### 3.3 专业术语密度

```text
术语密度 = 命中术语数 / token总数 × 100
```

密度越高，分数越高。

### 第 4 步：实现路由决策

对应文件：`src/router.py`。

路由不是简单“只调一个模型”，因为题目要求两个模型对比，所以本系统始终调用两个模型。路由主要决定：

- 是否强制术语表。
- 是否启用审校 Agent。
- 提示词严谨程度。

| 总分 | 路由 |
|---|---|
| <35 | 快速双译对比 |
| 35-69 | 标准双模型协作 |
| ≥70 | 专业文本严格审校 |

### 第 5 步：封装模型调用

对应文件：`src/llm_client.py` 和 `src/translator.py`。

为了能接多个模型，使用 OpenAI 兼容接口：

- 模型 A：速度快、便宜。
- 模型 B：质量更高或来自另一个厂商。

`.env` 中配置两组模型参数。如果没有 Key，`MOCK_MODE=true` 可以离线跑通流程。

### 第 6 步：实现模型调用中间件

对应文件：`src/metrics.py`。

中间件包住每次模型调用，记录：

- 模型名称
- 调用耗时
- 输入 token 估算
- 输出 token 估算
- 估算成本

估算成本公式：

```text
成本 = 输入token/1000 × 输入单价 + 输出token/1000 × 输出单价
```

### 第 7 步：实现审校评分规则

对应文件：`src/scoring.py`。

评分从 100 分开始扣：

1. 数字/单位遗漏：每处 -8。
2. 专业术语不一致：每处 -6。
3. 源语残留过多：-10 或 -20。
4. 译文长度异常：过短 -15，过长 -8。
5. 标点/括号结构错误：每类 -5。
6. 专有名词/缩写遗漏：每处 -4。
7. 重复/语病：每处 -5。
8. Markdown 结构丢失：每处 -8。

这一步是答辩重点，因为它证明“评分不是 LLM 随便说的”，而是可复现规则。

### 第 8 步：实现审校子 Agent

对应文件：`src/reviewer_agent.py`。

审校 Agent 不重新给总分，而是把扣分项归类成信达雅：

- 信：信息准确、术语、数字、专名。
- 达：结构完整、句意通顺。
- 雅：表达自然、无重复语病。

然后根据扣分项生成修改建议。

### 第 9 步：实现主流程 Pipeline

对应文件：`src/pipeline.py`。

主流程伪代码：

```python
complexity = evaluator.evaluate(text)
route = decide_route(complexity)
translations = translator.translate_many(route.call_models, text)
for translation in translations:
    score = scorer.score(text, translation)
    review = reviewer.review(text, translation, score)
best = choose_highest_score(translations)
return result
```

### 第 10 步：实现界面

对应文件：`src/app.py`。

界面分 4 个 tab：

1. 文本翻译对比。
2. Markdown 批量翻译。
3. 图片 OCR 翻译。
4. 10 段评测。

答辩时直接运行：

```bash
streamlit run src/app.py
```

## 4. 边界情况分析

| 边界情况 | 处理方式 |
|---|---|
| 空输入 | 抛出“输入文本不能为空”并在界面显示错误 |
| 没有 API Key | 使用 MOCK_MODE 离线演示 |
| 模型调用失败 | Streamlit 捕获异常并显示错误 |
| OCR 失败 | 返回 warning，用户仍可手动粘贴文本 |
| Markdown 代码块 | 保持原样，不翻译 |
| 术语表没命中 | 复杂度术语分低，但流程继续 |
| 两个模型分数相同 | 比较信评分，再比较耗时 |

## 5. 答辩讲解建议

5 分钟演示可以这样安排：

1. 30 秒：介绍系统目标和完整链路。
2. 1 分钟：输入普通文本，展示两个模型译文对比。
3. 1 分钟：输入专业文本，解释复杂度和术语扣分。
4. 1 分钟：展示 10 段评测结果和耗时统计。
5. 1 分钟：展示 OCR 或 Markdown 进阶功能。
6. 30 秒：说明评分规则可复现，不由 LLM 直接决定。
