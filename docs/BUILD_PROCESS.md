# BUILD_PROCESS：从零制作序号 21 系统的详细过程

这份文档可以直接作为你写项目报告或答辩讲稿的“制作过程”。

## 阶段一：需求确认

1. 打开课题表，找到序号 21。
2. 确认题目是“多模型协作翻译与审校系统”。
3. 把题目拆成四个核心问题：
   - 怎么判断文本难不难？
   - 怎么让两个模型翻译同一文本？
   - 怎么量化比较两个译文？
   - 怎么输出推荐译文和修改建议？
4. 再把进阶要求拆成四个加分功能：
   - 审校子 Agent。
   - 图片 OCR 翻译。
   - 批量文档翻译保持目录结构。
   - 统计模型耗时和成本。

## 阶段二：设计整体流程

系统流程如下：

```text
输入文本
  ↓
复杂度评估：句长、从句、术语密度
  ↓
路由决策：低/中/高复杂度
  ↓
模型 A 翻译 + 模型 B 翻译
  ↓
规则评分：数字、术语、残留、长度、格式等
  ↓
审校 Agent：信达雅评分与建议
  ↓
选择最佳译文
  ↓
输出对比表、评分表、推荐译文
```

## 阶段三：搭建项目目录

新建目录：

```text
translation_review_system/
├── src/
├── data/
├── docs/
└── tests/
```

每个目录的作用：

- `src/`：写系统代码。
- `data/`：放术语表和测试文本。
- `docs/`：放提交文档。
- `tests/`：放单元测试。

## 阶段四：准备数据

### 1. 术语表

创建 `data/term_glossary.csv`。

例子：

```csv
source_term,target_term,domain
artificial intelligence,人工智能,technology
clinical diagnosis,临床诊断,medicine
```

用途：

- 复杂度评估时统计专业术语密度。
- 审校评分时检查译文有没有采用标准译法。

### 2. 测试文本

创建 `data/benchmark_texts.jsonl`，准备 10 段不同领域文本。

领域建议：科技、医学、法律、经济、商业、环境、教育等。

## 阶段五：写复杂度评估模块

文件：`src/complexity.py`。

### 1. 句子长度

实现：

```text
平均句长 = token 总数 / 句子数
```

评分：

- 短句分低。
- 长句分高。

### 2. 嵌套从句数

用规则数这些标记：

- 英文：which、that、because、although、if。
- 中文：因为、虽然、如果、导致、其中。
- 标点：分号、冒号、括号。

### 3. 术语密度

实现：

```text
术语密度 = 命中术语数 / token 总数 × 100
```

最后得到：

```text
总复杂度 = 句长分 + 从句分 + 术语密度分
```

## 阶段六：写路由模块

文件：`src/router.py`。

规则：

- 0-34：低复杂度。
- 35-69：中复杂度。
- 70-100：高复杂度。

注意：题目要求对比两个模型，所以不管复杂度是多少，都调用模型 A 和模型 B。路由只改变提示词要求，比如是否强制术语表。

## 阶段七：写模型调用模块

文件：`src/llm_client.py`、`src/translator.py`。

### 1. 配置两个模型

在 `.env` 中写：

```env
MODEL_A_NAME=gpt-4o-mini
MODEL_A_API_KEY=
MODEL_B_NAME=gpt-4.1-mini
MODEL_B_API_KEY=
```

### 2. 构造提示词

提示词要包含：

- 源语言。
- 目标语言。
- 术语表。
- 是否必须使用术语。
- 待翻译文本。

### 3. 离线演示模式

如果没有 Key，就用 `MOCK_MODE=true`。这样系统可以跑通，但答辩时要说明“这是模拟译文，真实演示时可接 API”。

## 阶段八：写耗时和成本统计中间件

文件：`src/metrics.py`。

每次模型调用前记录开始时间，调用后记录结束时间。

```text
耗时 = 结束时间 - 开始时间
```

成本估算：

```text
成本 = 输入 token / 1000 × 输入单价 + 输出 token / 1000 × 输出单价
```

输出按模型汇总：

- 调用次数。
- 总耗时。
- 总成本。

## 阶段九：写审校评分模块

文件：`src/scoring.py`。

评分从 100 分开始扣。至少 5 条，本系统写了 8 条。

| 规则 | 扣分 |
|---|---:|
| 数字/单位遗漏 | 每处 -8 |
| 术语不一致 | 每处 -6 |
| 源语残留多 | -10 或 -20 |
| 译文长度异常 | -8 或 -15 |
| 括号/引号不成对 | 每类 -5 |
| 专有名词/缩写遗漏 | 每处 -4 |
| 重复/语病 | 每处 -5 |
| Markdown 结构丢失 | 每处 -8 |

答辩时重点讲：这些扣分都是代码规则实现的，不是让 LLM 自己打分。

## 阶段十：写审校子 Agent

文件：`src/reviewer_agent.py`。

把扣分项分成三类：

- 信：数字、术语、专名、源语残留。
- 达：长度、结构、格式。
- 雅：重复、语病、表达自然度。

然后生成建议，例如：

- “补回原文中的数字和单位。”
- “按术语表统一专业词汇。”
- “修复括号和列表结构。”

## 阶段十一：写主流程

文件：`src/pipeline.py`。

主流程要把所有模块串起来：

1. 输入文本。
2. 复杂度评估。
3. 路由决策。
4. 两个模型翻译。
5. 两个译文分别评分。
6. 审校 Agent 生成建议。
7. 选择分数最高的译文。
8. 返回结构化结果。

## 阶段十二：写前端界面

文件：`src/app.py`。

用 Streamlit 做 4 个页面：

1. 文本翻译对比。
2. Markdown 批量翻译。
3. 图片 OCR 翻译。
4. 10 段评测。

运行：

```bash
streamlit run src/app.py
```

## 阶段十三：写测试用例

至少准备 5 组核心测试：

1. 普通文本翻译。
2. 专业术语文本翻译。
3. 数字单位保持测试。
4. Markdown 结构保持测试。
5. 空输入/异常输入测试。

本项目还准备了 10 段 benchmark 文本用于对比两个模型评分与耗时。
